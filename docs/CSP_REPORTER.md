# CSP Violation Reporter

This script is a lightweight Node.js service designed to collect Content Security Policy (CSP) violation reports from browsers, log them locally, and notify via Telegram.

## Features

- **Detailed Notifications:** Sends formatted HTML messages to Telegram with icons and key violation details.
- **JSON Attachments:** Attaches the full original CSP report as a `.json` file to each Telegram message for deep analysis.
- **Local Logging:** Records every violation in `logs/csp-violations.log` for long-term tracking.
- **False-Positive Filtering:** Two tiers, both in `scripts/utils/csp-filters.mjs`. The **discard tier** (`getDiscardReason`) drops reports that cannot describe the site's own behavior — they never reach the log or Telegram. The **notification tier** (`getNotifySuppressReason`) keeps crawler reports in the log but off Telegram, so the evidence survives without paging anyone. The site's own pages are verified CSP-clean on a real browser, so neither category ever indicates an actionable issue.

  Discarded outright:
  - **Extension violations** — Browser extensions (`chrome-extension`, `moz-extension`, `safari-extension`, `webkit-extension`, etc., including truncated values), userscript managers (`user-script`), extension sandboxes (`sandbox eval code`) and antivirus injection (`kaspersky-labs.com`).
  - **Browser-internal violations** — Reports from `about:blank`/`about:srcdoc` frames, Firefox `resource://` scripts, and `blob:` URIs generated by extensions or DevTools.
  - **Prefetch false positives** — Same-origin prefetch violations caused by browsers lacking `prefetch-src` support (falls back to `default-src`), including null source-file cases and `prefetch-src` effective-directive reports.
  - **Injected third-party resources** — `data:` or remote (non-jmrp.io) fonts/media (the site restricts `font-src`/`media-src` to `'self'`), `connect-src` to `data:`, and known browser-translator/extension origins (Google/Yandex Translate, Perplexity, etc.).
  - **Injected inline styles** — `style-src-*` `'inline'` violations. The site emits styles only via nonce'd `<style>` or utility classes, so these are always extension-injected. Inline _script_ violations are deliberately **not** filtered (they may indicate real XSS).

  Logged but not notified:
  - **Crawler user-agents** — Googlebot, YandexBot/YandexRenderResourcesBot, bingbot, YisouSpider, Bytespider, AI crawlers, HTTP libraries, plus the bare Chromium template missing `Chrome/`.
  - **Crawler netblocks** — Google and Yandex crawler ranges, for fetchers that render with a browser user-agent.

- **Rate Limiting:** Notifications are deduplicated by _violation signature_ (`effective-directive` + `blocked-uri`), once every 10 minutes. Neither the client IP nor the document URI is part of the key.
- **Security Hardened:** Implements request body size limits (32KB) to prevent memory exhaustion (DoS) and escapes HTML input.
- **Zero Dependencies:** Uses native Node.js `http` and `https` modules. Includes a built-in `.env` parser to avoid external dependencies.

## Setup

### 1. Environment Variables

The script requires the following variables in your `.env` file:

```bash
TELEGRAM_BOT_TOKEN=your_bot_token
TELEGRAM_CHAT_ID=your_chat_id
CSP_REPORTER_PORT=58291 # Optional, defaults to 58291
```

### 2. Systemd Service

Create a service file at `/etc/systemd/system/csp-reporter.service`:

```ini
[Unit]
Description=CSP Violation Reporter Service
After=network.target

[Service]
Type=simple
User=root
WorkingDirectory=/var/www/jmrp.io
ExecStart=/usr/bin/node scripts/csp-reporter.mjs
Restart=on-failure
Environment=NODE_ENV=production

[Install]
WantedBy=multi-user.target
```

### 3. Nginx Configuration

To route reports to the service, add a location block to your Nginx site configuration:

```nginx
# CSP Report Endpoint (Proxy to local Node.js service)
location /csp-report {
    access_log off;
    proxy_pass http://127.0.0.1:58291/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
}
```

Then, update your `Content-Security-Policy` header to include the `report-uri`:

```nginx
add_header Content-Security-Policy "..."; report-uri /csp-report;" always;
```

## False-Positive Filters

The filter predicates live in `scripts/utils/csp-filters.mjs`. They are applied in two tiers:

| Tier      | Entry point                               | Effect                                      |
| --------- | ----------------------------------------- | ------------------------------------------- |
| Discard   | `getDiscardReason(report)`                | HTTP 204, **no log entry**, no notification |
| No-notify | `getNotifySuppressReason(report, ua, ip)` | HTTP 204, **logged**, no notification       |

Against a real 1146-entry production log the discard tier removed **98.9%** of reports. The no-notify tier was added afterwards, when the reports that survived turned out to drive 95% of the notifications as crawler traffic (see [Why crawlers are filtered at the notification layer](#why-crawlers-are-filtered-at-the-notification-layer)).

### 1. Extension Violations (`isExtensionViolation`)

Detects reports originating from browser extensions, userscript managers and antivirus suites by checking `source-file`/`blocked-uri` for:

- Extension protocol prefixes: `chrome-extension`, `moz-extension`, `safari-extension`, `safari-web-extension`, `webkit-extension`, `ms-browser-extension` (including truncated values without `://`).
- `<anonymous code>` (Firefox-injected extension scripts).
- `user-script` / `userscript` (Tampermonkey, Violentmonkey, Greasemonkey).
- `sandbox eval code` (Chromium extension sandbox).
- `kaspersky-labs.com` (Kaspersky Protection script injection — the single largest source in production).

### 2. Browser-Internal Violations (`isBrowserInternalViolation`)

Catches violations from browser-internal contexts:

- **`about:` pages** — `source-file`/`blocked-uri` is `"about"` (from `about:blank`/`about:srcdoc` frames, extension-injected iframes, DevTools).
- **`resource://`** — Firefox internal scripts and styles.
- **`blob:` URIs** — Generated by extensions or DevTools, not by page code.

### 3. Prefetch False Positives (`isPrefetchFalsePositive`)

Browsers that lack `prefetch-src` support (notably Firefox) fall back to `default-src` when evaluating prefetch requests. Since same-origin prefetches should be allowed, these are false positives. Matches when:

- `effective-directive` is `default-src` or `prefetch-src`, AND
- `blocked-uri` is same-origin, AND
- `source-file` matches Astro's prefetch module (`/page.[hash].js`), OR `source-file` is null/empty and `blocked-uri` looks like an HTML page path.

### 4. Injected Third-Party Resources (`isInjectedThirdPartyResource`)

The site's CSP restricts `font-src` and `media-src` to `'self'`, so any `data:` URI or remote (non-jmrp.io) font/media is injected by an extension or the browser's translator. Also covers `connect-src` to `data:` and known translator/extension origins (`translate.google.com`, `gstatic.com`, `yastatic.net`, `r2cdn.perplexity.ai`, `div.show`).

### 5. Injected Inline Styles (`isInjectedInlineStyle`)

`style-src-elem` / `style-src-attr` (and the legacy full-policy form) `'inline'` violations. The site emits styles only via nonce'd `<style>` elements or utility classes (enforced by the build pipeline and `security.spec.ts`), so any inline-style violation is extension-injected (dark-mode, translators, antivirus). Inline **script** violations are deliberately **not** filtered — they may indicate a real XSS and must always be surfaced.

## Why crawlers are filtered at the notification layer

Over the 49 days ending 2026-07-26, 490 reports survived the discard tier and produced **209 Telegram notifications**. Categorized:

| Source                                                    | Reports | Notifications | Share of notifications |
| --------------------------------------------------------- | ------: | ------------: | ---------------------: |
| Yandex crawlers (`YandexBot`, `YandexRenderResourcesBot`) |     168 |           167 |                  79.9% |
| Google rendering netblocks (browser UA, Google IPs)       |      60 |            29 |                  13.9% |
| Other crawlers (`YisouSpider`, `AdsBot-Google`)           |       2 |             2 |                   1.0% |
| Everything else (`eval`, real-browser SRI, scanners)      |     260 |            11 |                   5.3% |

Crawlers were **198 of 209** notifications (95%). Replaying the same log under the new policy yields **13** notifications, all from the "everything else" row.

Two root causes, both inherent to a per-request-nonce CSP plus crawler caching, neither reproducible in a browser:

- **Stale `_astro` chunks (SRI).** 173 of the 490 reports were SRI failures on just three content-hashed `page.[hash].js` chunks from previous builds. Crawlers re-render an HTML snapshot they cached before a redeploy; the chunk it names no longer exists.
- **Nonce mismatch (inline scripts).** Google's fetchers cache HTML and response headers independently, so a re-render can pair HTML holding nonce A with a policy carrying nonce B, blocking every inline script on the page.

They are filtered at the **notification** layer rather than in Nginx or the discard tier for three reasons:

1. Nginx cannot see the report body, only the UA/IP — it would have to drop the report before anything knows what the violation was.
2. Both root causes are inferences, not certainties. Keeping the reports in `logs/csp-violations.log` means the inference can be re-checked later; discarding them means it cannot.
3. If a crawler ever reports something genuinely new, the evidence is on disk. `pnpm csp:replay` re-derives the whole classification from that log at any time.

### Detection

- **`isBotUserAgent(ua)`** — crawler/automation user-agents. The keyword regex matches `bot`/`crawl`/`crawler`/`spider`/`slurp` as a token _suffix_ (`(?![a-z])`), because crawler names end with the keyword (`Googlebot`, `YandexBot`, `bingbot`, `YisouSpider`) and a leading `\b` never matches there. Names like `RobotVacuum` or `Robotics`, where letters follow, are not matched. Also matches an explicit token list (`curl/`, `python-requests`, `GPTBot`, `meta-externalagent`, …) and the bare Chromium template `AppleWebKit/537.36 … Safari/537.36` with no `Chrome/` token. Checked against all 411 distinct user-agents that have ever POSTed to `/csp-report`: 15 matched, all from Yandex, Google, Microsoft, Amazon, Facebook, Chinanet or `curl` — no browser was flagged.
- **`isCrawlerNetwork(ip)`** — Google and Yandex crawler netblocks, for fetchers that render with a browser user-agent. Google **Cloud** customer ranges (`34/35.x`) are deliberately excluded: those are rented VMs, i.e. exactly where a scanner or attacker would run from.

### Verifying a policy change

`scripts/csp-replay.mjs` replays a real log through the filter chain and notification policy and prints notifications before/after, the reason for every filtered report, the user-agents the crawler tier silenced, and a PASS/FAIL check that no non-crawler violation _kind_ stopped being notified:

```bash
pnpm csp:replay                        # defaults to logs/csp-violations.log
pnpm csp:replay path/to/other.log
```

Unit tests for the predicates: `pnpm test:unit`.

## Usage

Once running, you can test the reporter using `curl`:

```bash
curl -X POST https://yourdomain.com/csp-report \
  -H "Content-Type: application/csp-report" \
  -d '{"csp-report":{"document-uri":"https://yourdomain.com/test","violated-directive":"script-src","blocked-uri":"https://evil.com/test.js"}}'
```
