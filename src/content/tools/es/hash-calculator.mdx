  - question: "¿Cuándo debo usar un hash CSP en lugar de un nonce?"
    answer: "Usa un hash para scripts o estilos inline cuyo contenido nunca cambia, así puedes permitirlos sin \"unsafe-inline\". Si el script contiene valores dinámicos como un ID de usuario, usa un nonce, porque cualquier cambio en el contenido invalida el hash."
  - question: "¿Por qué mi script inline se sigue bloqueando tras añadir el hash?"
    answer: "Los hashes CSP requieren una coincidencia exacta byte a byte, así que incluso un espacio o salto de línea de más genera un hash distinto y el navegador bloquea el script. Asegúrate de calcular el hash solo del contenido interno, sin las etiquetas \"<script>\" o \"<style>\"."
  - question: "¿Cuál es la diferencia entre un hash CSP y un hash SRI?"
    answer: "Un hash CSP (SHA-256 en base64) autoriza código inline específico en tu Content Security Policy. Un hash SRI (normalmente SHA-384) va en el atributo \"integrity\" de una etiqueta script o link externa para verificar que el archivo descargado no ha sido manipulado."
  - question: "¿Se envía el contenido de mi script a un servidor?"

  - question: "¿Qué algoritmo de hash debo elegir?"
    answer: "SHA-256 es la opción estándar y más compatible para CSP. SHA-384 y SHA-512 también son válidos y se usan habitualmente para Subresource Integrity, pero SHA-256 basta para casi todos los casos de uso de CSP."

<h2>Acerca de esta herramienta</h2>
<p>
  Cuando necesitas permitir scripts o estilos inline específicos en tu Content
  Security Policy (CSP) sin usar <code>'unsafe-inline'</code>, puedes utilizar
  hashes criptográficos. Esta herramienta calcula el hash SHA-256 de tu contenido
  en el formato base64 exacto que esperan los navegadores.
</p>

<h2>¿Por qué usar hashes en CSP?</h2>
<p>
  Los hashes proporcionan una forma segura de permitir scripts inline específicos
  sin abrir la puerta a ataques XSS. Cada hash es único para su contenido exacto,
  lo que garantiza que solo se ejecuten los scripts autorizados.
</p>
