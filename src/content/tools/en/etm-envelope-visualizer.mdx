<h2>About This Tool</h2>
<p>
  Every file in the vault is an <strong>encrypt-then-MAC</strong> envelope:{" "}
  <code>[ver][iv][hmacTag][cipher]</code>. This tool builds one for real in your
  browser — it derives separate <code>encKey</code> and <code>macKey</code>{" "}
  sub-keys, encrypts the secret with <strong>AES-256-CBC</strong>, and
  authenticates the version byte, IV, and ciphertext together with{" "}
  <strong>HMAC-SHA256</strong>.
</p>
<p>
  It is the interactive companion to the article{" "}
  <a href="/blog/011-encrypt-then-mac-vault/">A Vault File That Fails Closed: Encrypt-then-MAC on an MCU</a>.
</p>

<h3>How do I use it?</h3>
<ol>
  <li>
    Type a secret and a passphrase, and set the <strong>authenticated context</strong>{" "}
    (record type, slot, generation). The envelope re-seals live as you type.
  </li>
  <li>
    <strong>Click any byte</strong> to flip it, or pick one of the seven{" "}
    <strong>attacks</strong>: flip a cipher/IV byte, forge the tag, truncate the
    ciphertext, move the file to another slot, change its record type, or roll
    back its generation.
  </li>
  <li>
    Watch the <strong>read-path verdict</strong>. Under encrypt-then-MAC every
    attack <strong>fails closed</strong> — and the tool tells you <em>why</em>{" "}
    each one fails (a different reason for each).
  </li>
  <li>
    Flip the read path to <strong>decrypt-first</strong> and press{" "}
    <strong>Run the padding-oracle attack</strong>: a real Vaudenay attack
    recovers the last plaintext block <em>byte-by-byte</em> using only the
    padding-valid/invalid signal — no key. Switch back to encrypt-then-MAC and
    the same attacker goes silent.
  </li>
</ol>

<h3>What does it show?</h3>
<ul>
  <li>
    <strong>Key separation</strong> — one passphrase becomes a master key, which
    fans out into distinct <code>encKey</code> and <code>macKey</code> sub-keys.
  </li>
  <li>
    <strong>Context binding</strong> — the tag covers{" "}
    <code>ver ‖ recordType ‖ slotId ‖ generation</code>, so relocating,
    retyping, or rolling back a file breaks the MAC even though the ciphertext is
    pristine.
  </li>
  <li>
    <strong>Verify-before-decrypt &amp; fail-closed</strong> — the tag is checked
    first, so a tampered file never reaches the AES-CBC decrypt path, and any
    failure returns nothing.
  </li>
  <li>
    <strong>The doom path</strong> — decrypt-first runs the cipher on attacker
    bytes before the MAC, exposing a genuine <strong>padding oracle</strong>.
  </li>
  <li>
    <strong>CBC malleability</strong> — flipping an IV byte flips the matching
    plaintext byte of block 0 by the same amount: the attacker's lever.
  </li>
</ul>

<h3>The construction, in formulas</h3>
<p>Sealing (write path):</p>
<pre><code>{`encKey = HMAC(master, "vault-enc")
macKey = HMAC(master, "vault-mac")
C      = AES-256-CBC-Encrypt(encKey, IV, PKCS7(P))
tag    = HMAC-SHA256(macKey, ver ‖ recordType ‖ slotId ‖ generation ‖ IV ‖ C)
file   = [ver] [IV] [tag] [C]`}</code></pre>
<p>Reading under encrypt-then-MAC (verify, then decrypt):</p>
<pre><code>{`tag' = HMAC-SHA256(macKey, context ‖ IV ‖ C)
if not constant_time_equal(tag', tag): reject   // fail closed, no plaintext
P    = unpad(AES-256-CBC-Decrypt(encKey, IV, C))`}</code></pre>
<p>Why the order is the whole game — the work an attacker faces:</p>
<ul>
  <li>
    Forge a tag without <code>macKey</code>: a brute force of{" "}
    <code>2^256</code> (HMAC-SHA256) — infeasible.
  </li>
  <li>
    Padding oracle (decrypt-first): ~1 bit per query, ≤ 256 queries per byte → a
    16-byte block in ≤ ~4096 queries.
  </li>
  <li>
    Encrypt-then-MAC removes the oracle outright: for a forged file the decrypt
    step is <em>unreachable</em>, so the attack drops from linear to impossible.
  </li>
</ul>

<h3>Why CBC malleability is the lever</h3>
<p>
  In CBC, <code>P_i = Decrypt(C_i) ⊕ C_(i-1)</code> (with{" "}
  <code>C_(-1) = IV</code>). So <code>ΔP_i = ΔC_(i-1)</code>: flipping a byte of
  the previous block — or of the IV, for block 0 — flips the same byte of the
  plaintext by the same amount, predictably. That controlled change is exactly
  what lets a padding oracle walk the plaintext out one byte at a time.
</p>
