faq:
  - question: "Are my WireGuard keys safe with this generator?"
    answer: "Yes. The tool runs entirely in your browser and sends no data to any server. By default it lets RouterOS auto-generate the keys on the device, so private keys never need to be entered into the tool at all."
  - question: "What is the difference between full tunnel and split tunnel?"
    answer: "Full tunnel routes all client traffic through the VPN (AllowedIPs = 0.0.0.0/0 and ::/0), while split tunnel only routes the specific subnets you list. Use split tunnel when clients should reach your LAN without sending their general internet traffic over the VPN."
  - question: "What should I put in AllowedIPs for a peer?"
    answer: "On the client config, AllowedIPs defines which destinations are sent through the tunnel: use 0.0.0.0/0, ::/0 for a full tunnel or just your VPN and LAN subnets for split tunnel. On the router side, each peer's allowed address is its assigned VPN IP, which the generator fills in automatically."
  - question: "How many peers can I add?"
    answer: "You can add unlimited peers. Each client device gets a unique auto-assigned IP address and its own .conf file, with optional per-peer customization."
  - question: "How does the generator calculate the tunnel MTU and the MSS clamps?"
    answer: "It starts from your WAN MTU, the actual-mtu RouterOS reports for the WAN interface (1500 on Ethernet or fiber, 1492 on standard PPPoE), and subtracts the WireGuard overhead for the address family clients use to reach the endpoint: 60 bytes when the endpoint is IPv4 only, 80 when it has an IPv6 address or the client roams. A 1500 WAN with a dual-stack endpoint gives a 1420 tunnel MTU. It then writes two MSS clamp rules, because /ip firewall mangle never sees IPv6 traffic: one in /ip firewall mangle at the MTU minus 40 (1380) and one in /ipv6 firewall mangle at the MTU minus 60 (1360), the second only when IPv6 is enabled. Every client .conf also gets an MTU = line, because without it the iOS and Android apps fall back to 1280."
  - question: "Why does the router peer use responder=yes instead of persistent-keepalive?"
    answer: "Keepalive belongs on the side behind NAT, which for a phone or a laptop is the client, so each .conf keeps PersistentKeepalive (25 seconds by default) and the router publishes it as client-keepalive for the QR code. When the router sends keepalive packets itself, it keeps retrying handshakes towards the last endpoint a roaming client used, long after that address has gone dead. With responder=yes the router answers handshakes but never starts them; the property exists since RouterOS 7.15 and stops the retries from 7.17. The site-to-site preset turns it off, because there this router may have to call the peer. The client-mtu property, which carries the MTU into the QR code, needs RouterOS 7.25 or later: on an older version turn that option off, since RouterOS rejects the whole command when it contains a parameter it does not know, and the MTU = line in the .conf still does the job."

<h3>Which WAN MTU and endpoint family should I enter?</h3>
<p>
  WireGuard adds 60 bytes to every packet that travels over IPv4 (20 IP, 8 UDP,
  16 WireGuard header, 16 authentication tag) and 80 to every packet that
  travels over IPv6, whose header is 20 bytes longer. What matters is the family
  of the encrypted packet crossing the Internet, and the endpoint each client
  dials decides it: a name with only an A record, or an IPv4 address, travels
  over IPv4, while a name with an AAAA record, or an IPv6 address, can travel
  over IPv6 (a name with both A and AAAA records can arrive over either family),
  which calls for the 80-byte figure. The one exception to the IPv4 case is a
  phone on an IPv6-only mobile network, which translates IPv4 into IPv6 on the
  device and sends the packet over IPv6 even when the endpoint is IPv4, so
  choose IPv6 or dual-stack for anything that roams. The interface MTU is shared
  by every peer, so it has to fit the worst case. The MSS is then the tunnel MTU
  minus 40 for IPv4 traffic inside the tunnel (20 IP plus 20 TCP) and minus 60
  for IPv6 traffic (40 IP plus 20 TCP).
</p>

<p>
  The MSS clamps cover TCP only. UDP traffic such as QUIC (HTTP/3), DNS and VoIP
  depends on the interface MTU itself, which is why the MTU has to be right even
  with the clamps in place. The client MTU defaults to the tunnel MTU and goes
  into each <code>.conf</code> as <code>MTU =</code>: without that line the iOS
  and Android apps use 1280, and the desktop apps subtract 80 from their own
  network link, which knows nothing about your WAN.

<h3>Configuration Sections Generated</h3>
<ul>
  <li>
    <strong>Script header</strong>: the oldest RouterOS version that accepts
    every command in the script: 7.21 when a peer gets the
    <code>client-*</code> properties (<code>client-allowed-address</code>
    arrived in 7.21), otherwise 7.17 with <code>responder=yes</code> or 7.15
    without it (peer names), plus 7.25 when it includes
    <code>client-mtu</code>
  </li>
  <li>
    <strong>Interface creation</strong>: WireGuard interface with its listen
    port and an MTU worked out from your WAN, with the calculation written as a
    comment above it
  </li>
  <li>
    <strong>IP addressing</strong>: IPv4 and IPv6 (ULA) addresses on the
    interface
  </li>
  <li>
    <strong>IPv6 pool</strong>: address pool for IPv6 prefix delegation
  </li>
  <li>
    <strong>Interface lists</strong>: VPN and LAN list membership for firewall
    rule matching
  </li>
  <li>
    <strong>Address lists</strong>: firewall address list for FastTrack and rule
    matching
  </li>
  <li>
    <strong>Firewall input</strong>: accept WireGuard UDP port on IPv4 and IPv6
  </li>
  <li>
    <strong>Firewall forward</strong>: VPN to Internet, VPN to LAN, and reply
    rules
  </li>
  <li>
    <strong>NAT/masquerade</strong>: IPv4 masquerade and NAT66 for IPv6
  </li>
  <li>
    <strong>MSS clamping</strong>: one <code>change-mss</code> rule in
    <code>/ip firewall mangle</code> at the tunnel MTU minus 40 and, with IPv6
    on, another in <code>/ipv6 firewall mangle</code> at the tunnel MTU minus
    60. Each one matches only SYN packets whose MSS is above the new value,
    because
    <code>change-mss</code> can only lower it
  </li>
  <li>
    <strong>RAW rules</strong>: skip flood protection for WireGuard port
  </li>
  <li>
    <strong>Peer definitions</strong>: all peers with
    <code>responder=yes</code> (or <code>persistent-keepalive</code> when the
    router has to initiate) and client properties for QR code generation,
    <code>client-mtu</code> included on RouterOS 7.25 or later
  </li>
  <li>
    <strong>Client files</strong>: one <code>.conf</code> per peer with
    <code>MTU =</code> and <code>PersistentKeepalive =</code> lines
  </li>
</ul>
